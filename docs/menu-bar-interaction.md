# 状态栏交互建议

已按用户批准方案实现，且按后续纠正沿用现有折叠开关管理展开/收起，不新增「展开全部」入口。本机 Apple 签名版本已更新。验证过程仅后台扫描及自动测试，没有自动打开第三方菜单或切换窗口。

## 已确认的问题

- 截图中的条目只有名称，不能区分静态应用入口与当前状态栏项目。
- `PanelView.menuBarSection` 所有条目的点击都调用 `revealMenuBarTemporarily()`，没有使用被点击项目的身份。点飞书、Magpie 或 Wi-Fi 得到完全相同的结果。
- 固定 12 秒自动重新折叠与用户完成原生菜单操作没有关联，不能把倒计时当作菜单关闭条件。
- 本机飞书和 Magpie 的原状态栏元素均公开 `AXPress`，但本轮读取的 Title 为空，Help/Description/Value 未提供通知数量。公开点击动作不等于已验证隐藏位置下菜单能正确出现。

## 建议的交互契约

1. 打开 Hasp：每行表示一个原生状态栏项目，优先显示可取得的原图标、名称及真实状态。状态无法取得时省略，不把未知解释成没有通知或已关闭。
2. 点选项目：关闭 Hasp 面板，并调用该项目原生点击动作，打开它自己的菜单或弹窗。左键行为保持原应用语义；不统一改成打开应用主窗口。
3. 操作原菜单：保持可操作直到菜单关闭、Esc 取消或用户点击外部。若必须恢复原菜单栏才能正确定位菜单，则把恢复过程作为这次菜单操作的一部分，无需用户第二次找图标。菜单或子菜单仍在使用时不执行倒计时折叠。
4. 操作结束：恢复之前的折叠意图。全局展开/收起沿用原折叠开关；条目右键提供「打开应用主窗口」。

目标流程是「点飞书 → 飞书原生菜单 → 操作结束后恢复折叠」。键盘 Enter 与行点击一致，Esc 退出菜单；状态变化不挪动键盘焦点，不仅用颜色表达状态。

## 状态同步范围

- 系统项目用对应系统接口读取网络、音量、电池、专注模式等可获得状态；示例文字只是建议，不是本轮实测值。
- 第三方项目同步其公开的标题、提示、值和状态变化。能获取原状态图像时优先保留图像上的红点、文字或数字；无法获取时用应用图标回退，并且不宣称它反映实时通知。
- 不从应用名或静态图标猜测未读数，不把 Hasp 设计成读取所有应用通知内容的统一通知中心。Apple 的 UNUserNotificationCenter 面向调用应用自己的通知，不能据此承诺获取任意第三方通知。
- 状态刷新优先使用原生变更通知，面板可见时做有限刷新；观察支持、状态图像来源以及隐藏图标的原生菜单位置均需实现阶段逐个验证。

## 实施顺序及验收

已完成原生动作转发、菜单/弹窗生命周期跟踪、退出时恢复折叠、原折叠开关、行内应用图标、公开状态文字及面板可见时的有限刷新。状态 API 提供电量、音量和可获取的 Wi-Fi 状态；第三方未公开的未读数留空。当前图像为所属应用图标，不冒充带实时通知角标的原始状态栏图像。

后台验证确认辅助功能权限保留，飞书、Magpie 以及本机 Wi-Fi/电池/声音/专注模式均有原生点击入口；真实电量和音量可读。菜单生命周期测试涵盖长时间操作、子菜单、Esc/外部点击及无菜单动作。真实第三方弹出菜单的位置和完整操作流程仍需用户点击验收，以遵守不抢屏要求。

原生动作优先，不复制第三方菜单。入口缺失或失败时回到 Hasp 给出可通过原折叠开关展开后点击原图标的明确提示。

验收重点：点不同项目打开各自菜单；操作超过 12 秒不被折叠打断；退出后恢复折叠；变化的状态来自真实来源；未公开通知数据的应用不显示虚构未读数；除用户点击外不前置任何应用。飞书、Magpie 和系统 Wi-Fi 是首批验证项目。

## 提前折叠与卡顿修复

取消了「0.75 秒内没检测到弹窗就折叠」的推断；AX 超时也不算关闭。菜单观察覆盖所属应用的 helper 与主进程，并用菜单对象身份去重打开/关闭事件。未知状态不推进自动关闭确认。

系统偏好操作由多次 defaults 子进程改成后台 CFPreferences 批量提交，主线程不等待它们。菜单窗口和 AX 探测也在后台执行，同一时刻最多一个探测请求。先等待 Hasp 玻璃面板关闭，再恢复原状态栏和打开原菜单，避免两段布局变化同时进行；重新打开 Hasp 会取消未完成的交接。

本机只读对照测量中，旧方式读取 9 项偏好耗时约 79–88 ms，新方式含同步缓存刷新约 0.12 ms。该数据是偏好读取耗时，不是端到端动画帧率测量。新增回归覆盖长时间缺少数据、菜单已出现后的 AX 超时、重复事件、子菜单以及偏好域隔离。
